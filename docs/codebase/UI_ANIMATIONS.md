This document provides a low-level, technical breakdown of the double-buffered rendering pipeline, heap memory optimization strategies, custom word-wrap engines, and animated sprite rendering routines used in the Table-Bondhu firmware.

## 1. Double Buffering & Flicker Mitigation

### A. The Challenge: SPI Bus Overhead & Flickering
Drawing directly to a physical screen over an SPI bus is slow. Redrawing the background, avatar, and clock text pixel-by-pixel causes noticeable flickering, as the user can see the screen clearing and redrawing.

### B. The Solution: TFT_eSprite (Off-Screen Canvas)
We create a virtual screen buffer (canvas) in the ESP32's internal RAM called `faceSprite` using the `TFT_eSPI` library. All drawing operations (clearing the screen, rendering Pikachu bitmaps, drawing speech bubbles, and rendering text) are done inside this RAM buffer. 
Once the frame is fully built in RAM, we push the completed buffer to the physical screen over SPI in a single operation:

```
┌──────────────────────────────────────────────────────────────┐
│                      ESP32 SRAM                              │
│                                                              │
│  Draw BG ──► Draw Pikachu ──► Draw Bubble ──► Draw Clock     │
│                                                              │
│                     ┌──────────────┐                         │
│                     │  faceSprite  │                         │
│                     └──────┬───────┘                         │
└────────────────────────────┼─────────────────────────────────┘
                             │
                             │ SPI DMA Transfer (pushSprite)
                             ▼
                ┌──────────────────────────┐
                │    Physical ST7735 TFT   │
                └──────────────────────────┘
```

```cpp
// --- Double Buffered Push (gemini_LLM_btn.ino: Lines 312 - 328) ---
faceSprite.fillSprite(COLOR_BG); // 1. Clear offscreen canvas

// 2. Draw active elements to the canvas
pushThemedImage(faceSprite, 0, 0, 128, 110, CURRENT_IDLE); 
drawClockOverlay();

// 3. Push the fully rendered frame to the physical display
faceSprite.pushSprite(0, 0); 
```

## 2. Dynamic Heap Memory Allocation

The ESP32 has 520KB of SRAM. A full 16-bit color buffer for a $128\times 160$ display requires $128 \times 160 \times 2 \text{ bytes} = 40.96\text{KB}$ of continuous RAM. Since the ESP32's heap can become fragmented over time, keeping a large block of RAM allocated permanently for the sprite can cause allocations to fail elsewhere in the code.
To save RAM, we adjust the sprite size dynamically based on the current UI state:

*   **Active States (Clock, Listening, Talking, Timer):** The sprite is sized at **$128\times 110$** ($28.16\text{KB}$). This leaves the bottom 50 pixels of the screen free to render speech bubbles and scrolling text.
*   **Sleeping & Sleep Summary States:** The sprite is enlarged to **$128\times 160$** ($40.96\text{KB}$) to support full-screen rendering.

```cpp
// --- Dynamic Sprite Re-allocation (gemini_LLM_btn.ino: Lines 231 - 250) ---
void setAppState(AppState newState) {
  AppState oldState = currentState;
  currentState = newState;
  
  // Clean up existing sprite from memory
  faceSprite.deleteSprite();
  
  if (newState == STATE_SLEEPING || newState == STATE_SLEEP_SUMMARY) {
    // Allocate a full-screen sprite (128x160)
    faceSprite.createSprite(128, 160);
  } else {
    // Allocate a partial sprite (128x110), leaving room at the bottom
    faceSprite.createSprite(128, 110);
  }
  
  stateTimerMs = millis(); // Reset state duration timer
  needRedraw = true;       // Force redraw on next frame loop
}
```

## 3. Text Wrapping & Pagination Engine

The ST7735 display has a width of 128 pixels. Using a standard 8-pixel font allows a maximum of 16 characters per line. Long sentences generated by the LLM must be wrapped and divided into pages to fit on the screen.
The firmware splits incoming text into lines and groups them into pages (max 4 lines per page). The user can press the **BOOT** button (GPIO 0) to flip to the next page.

```
Incoming Text: "Sure! I can help you water the plants at 6pm today."

Processed Pages:
┌────────────────────┐   BOOT Pin (Short Press)   ┌────────────────────┐
│ Sure! I can help   │ ─────────────────────────► │ at 6pm today.      │
│ you water the      │                            │                    │
│ plants             │                            │                    │
└────────────────────┘                            └────────────────────┘
       Page 0                                            Page 1
```

```cpp
// --- Character Wrapping Engine (gemini_LLM_btn.ino: Lines 275 - 310) ---
void formatBubbleText(String rawText) {
  bubbleLineCount = 0;
  String currentLine = "";
  
  int startIdx = 0;
  while (startIdx < rawText.length()) {
    int nextSpace = rawText.indexOf(' ', startIdx);
    String word = (nextSpace == -1) ? rawText.substring(startIdx) : rawText.substring(startIdx, nextSpace);
    
    // Check if adding the word exceeds the 18-character line limit
    if (currentLine.length() + word.length() + 1 > 18) {
      bubbleLines[bubbleLineCount++] = currentLine;
      currentLine = word;
    } else {
      if (currentLine.length() > 0) currentLine += " ";
      currentLine += word;
    }
    
    if (nextSpace == -1) break;
    startIdx = nextSpace + 1;
  }
  if (currentLine.length() > 0) {
    bubbleLines[bubbleLineCount++] = currentLine;
  }
}
```

## 4. Pikachu Sprite Bitmaps & Frame Cycles

All character frame assets are stored in flash memory as raw 16-bit RGB565 arrays in [images.h](file:///F:/__KUET%20Assignments/IOT/Table-Bondhu-main/gemini_LLM_btn/images.h).

*   **Blinking Animation:** In the idle state, the screen cycles through frames to make the avatar blink at random intervals.
    `pika_idle` (eyes open) $\rightarrow$ `pika_half_blink` (eyes half-closed) $\rightarrow$ `pika_smile_blink` (eyes closed) $\rightarrow$ `pika_idle`.
*   **Talking Animation:** When the server streams voice output, the display mouth cycles through frames to simulate speech:
    `pika_idle` $\rightarrow$ `pika_talk_20` $\rightarrow$ `pika_talk_60` $\rightarrow$ `pika_talk_100` $\rightarrow$ `pika_talk_blink`.
*   **Breathing Animation (Sleep):** In sleep mode, the screen periodically toggles between two frames every 1500ms to simulate breathing:
    `pika_sleep_1` (chest contracted) $\leftrightarrow$ `pika_sleep_2` (chest expanded).
*   **Waving Animation (Intro):** Plays when the device connects to the server, cycling through three frames to wave at the user:
    `pika_wave_1` $\rightarrow$ `pika_wave_2` $\rightarrow$ `pika_wave_3`.

## 5. Comprehensive Teacher Viva Q&A

### Q1: Why is double buffering necessary on microcontrollers with small displays?
**Answer:** The SPI bus runs at a limited clock speed (typically 10–20MHz for the ST7735). Sending pixel data directly over SPI takes time. If we clear the screen and draw elements one-by-one directly to the physical display, the user will see a visible "refresh sweep" (flickering). Double buffering draws everything in internal RAM first, then sends the completed image to the display in a single transfer. This makes the UI update instantly and eliminates flickering.

### Q2: What is RGB565, and why is it used instead of standard 24-bit RGB888?
**Answer:** Standard RGB888 uses 24 bits (3 bytes) per pixel. A $128\times 160$ display would require $61.4\text{KB}$ of storage per frame. 
**RGB565** uses 16 bits (2 bytes) per pixel: 5 bits for Red, 6 for Green, and 5 for Blue (Green gets 6 bits because the human eye is more sensitive to green variations). This reduces the memory footprint by 33% (down to $40.9\text{KB}$ per frame), which speeds up SPI transfers and saves storage space in flash memory.

### Q3: Why does your code call `deleteSprite()` before creating a new one?
**Answer:** The ESP32's memory is divided into blocks (heap). Creating a sprite allocates a large block of continuous memory. If we create a new sprite without calling `deleteSprite()`, the old sprite remains in memory, leading to a memory leak. Over time, this would consume all available RAM and crash the microcontroller. Calling `deleteSprite()` frees the memory block back to the heap before allocating a new one.

### Q4: How is word wrapping calculated in your pagination engine?
**Answer:** We split the text string into words using spaces as delimiters. We keep a running count of characters in the current line. If adding the next word exceeds our limit (18 characters), we save the current line to our line array and start a new line with the word. This ensures text stays within the borders of the speech bubble and wraps cleanly without cutting words in half.
